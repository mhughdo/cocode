The key design idea is:

```text
preset = base review protocol
       + selected reviewer roles
       + preset-specific prompt overlay
       + knowledge packs
       + context-builder policy
       + verification policy
       + output policy
```

This follows the multi-agent book’s guidance: use explicit workflow structure, role specialization, context engineering, structured outputs, completion criteria, observability, and verification instead of loose agent chat. The book is especially relevant here because it says prompts should encode workflow phases, progress tracking, completion criteria, and error handling, and that long software-engineering tasks need context engineering and external verification to avoid early stopping or confident but incomplete reviews.  It also recommends matching orchestration pattern to task requirements and using explicit task management, termination, and human delegation patterns to prevent runaway execution.

For Go-specific presets, I grounded the checklist in official Go review guidance, including error handling, contexts, goroutine lifetimes, panics, imports, comments, and other common review comments. ([Go][1]) The Go performance preset should also ask agents to distinguish “proven regression” from “needs profiling/benchmark,” since Go’s own diagnostics docs frame tracing and profiling as tools for finding latency, utilization, and bottlenecks that are not always obvious from code inspection alone. ([Go][2])

For PostgreSQL presets, the Query Performance role should ask agents to reason from concrete query shape: tables, filters, joins, sort, limit, pagination, existing indexes, and whether the query runs in a loop. PostgreSQL’s docs describe `EXPLAIN` as the way to inspect the plan generated by the planner, including scan strategy, join algorithms, estimated cost, and optional actual runtime data via `ANALYZE`; the index docs also warn that indexes improve retrieval but add system overhead, so agents should not recommend indexes casually. ([PostgreSQL][3]) The migration preset should explicitly check table-rewrite and lock risks, concurrent index creation, and safe backfill/validation strategy; PostgreSQL docs note that some `ALTER TABLE` changes can be fast metadata-only operations, while volatile defaults and type changes can require rewriting rows, and `CREATE INDEX CONCURRENTLY` avoids write-blocking locks with important caveats. ([PostgreSQL][4])

For security presets, OWASP is the right baseline: the OWASP Code Review Guide is specifically aimed at people responsible for code reviews and focuses on identifying vulnerabilities during manual review. ([OWASP Foundation][5]) The security knowledge pack should include SQL injection, authentication, authorization, secrets, logging, SSRF, command injection, path traversal, webhook validation, token/session handling, and tenant isolation. OWASP’s SQL injection guidance strongly prefers prepared statements/parameterized queries, and its authorization guidance emphasizes least privilege, deny-by-default, permission checks on every request, and tests for authorization logic. ([OWASP Cheat Sheet Series][6]) For Go/Postgres apps specifically, Go’s database docs also warn against building SQL with `fmt.Sprintf` and recommend passing parameter values separately to `database/sql` functions. ([Go][7])

## Recommended role set

The document defines many roles, but I would ship these first:

| Role                                      | Purpose                                                                                                      |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Context Discovery Agent**               | Builds unbiased context: changed files, call sites, tests, routes, middleware, queries, migrations, configs. |
| **Go Correctness & Idioms Reviewer**      | Finds Go correctness, error handling, context, resource cleanup, API, and maintainability issues.            |
| **Go Performance Reviewer**               | Finds CPU, memory, allocation, serialization, hot-path, I/O, and DB-loop regressions.                        |
| **Go Concurrency Reviewer**               | Finds goroutine leaks, races, blocking channels, cancellation bugs, lock risks, worker lifecycle issues.     |
| **PostgreSQL Query Performance Reviewer** | Finds bad query shape, missing/wrong indexes, N+1 queries, unbounded scans, pagination issues.               |
| **PostgreSQL Migration Safety Reviewer**  | Finds unsafe schema changes, blocking indexes, table rewrites, backfill risks, rollout incompatibility.      |
| **Security Reviewer**                     | Finds injection, auth, authorization, secrets, unsafe external calls, logging and exposure risks.            |
| **AuthZ & Tenant Isolation Reviewer**     | Deeply traces route → middleware → handler → query → response for access-control failures.                   |
| **Testing & Regression Reviewer**         | Finds missing regression, negative, boundary, migration, concurrency, and security tests.                    |
| **Evidence Verifier**                     | Checks whether findings are true, false, plausible, duplicate, or need human judgment.                       |
| **Counter-Evidence Skeptic**              | Actively tries to disprove high-impact findings before they are marked verified.                             |
| **Finding Synthesizer**                   | Deduplicates, ranks, rewrites, and prepares final user-facing findings.                                      |
| **Copy Fix Packet Writer**                | Converts accepted findings into paste-ready instructions for your external coding agent.                     |

The Evidence Verifier and Counter-Evidence Skeptic roles are important because they reduce the exact pain point you described: agents often make claims that sound plausible, and the human has to scout the codebase to verify them. cocode should make verification a first-class workflow step.

## Evidence Map addition

I updated the preset design around the new **Evidence Map** screen. Presets now require reviewer roles to emit graph-friendly evidence objects, not just prose.

Example for an auth finding:

```text
router/setup.go L34-L67
  registers -> routes/billing.go L118-L142

routes/billing.go L118-L142
  missing_guard -> middleware/auth.go L22-L48

routes/billing.go L118-L142
  calls -> handlers/payouts.go L210-L268

billing_routes_test.go L45-L102
  covers -> routes/billing.go L118-L142
```

This means each finding can power three views:

```text
Finding card        -> concise claim, severity, agent agreement
Finding detail      -> changed code, evidence, draft comment, suggested fix
Evidence Map        -> route/call/query/test graph that proves or weakens the claim
```

## How presets should be implemented

I recommend storing presets as data, not hardcoding them into agents:

```text
cocode-presets/
  presets/
    standard-pr-review.yaml
    security-auth-focus.yaml
    go-performance-deep-dive.yaml
    postgres-query-performance.yaml
    postgres-migration-safety.yaml

  roles/
    context-discovery.md
    go-correctness.md
    go-performance.md
    go-concurrency.md
    postgres-query-performance.md
    postgres-migration-safety.md
    security.md
    authz-tenant-isolation.md
    evidence-verifier.md
    finding-synthesizer.md
    copy-fix-packet-writer.md

  knowledge/
    go-correctness.md
    go-performance.md
    go-concurrency.md
    postgres-query-performance.md
    postgres-migration-safety.md
    security-baseline.md
    testing-baseline.md

  schemas/

    evidence_map.schema.json
```

This keeps Phase 1 simple: render a self-contained prompt for each non-interactive CLI run. Later, the same preset/role system can work with Codex App Server, ACP, MCP, A2A, or provider SDK adapters because the preset defines the task, context, and output contract rather than the transport.

## Example role prompt

```text
ROLE: PostgreSQL Query Performance Reviewer

Review the PR for PostgreSQL query performance issues.

For each changed query, identify:
- tables involved
- filters
- joins
- sort/order clauses
- limits
- pagination style
- expected cardinality if inferable
- existing relevant indexes
- whether the query is inside a loop
- whether the query returns unbounded rows

Look for:
- missing indexes
- wrong index column order
- N+1 queries
- OFFSET pagination on large tables
- unbounded SELECTs
- SELECT * over-fetching
- query builder changes that defeat parameterization or plan stability
- JSONB/text search without appropriate index strategy
- COUNT or aggregation on large tables without constraints

Do not recommend an index unless you checked existing indexes or note that index information is missing. Mention write overhead for suggested indexes.

If EXPLAIN data is unavailable, request EXPLAIN or mark as "needs query plan" rather than overclaiming.
```
